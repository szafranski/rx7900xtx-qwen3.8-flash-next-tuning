**Verdict:** go ahead with ExecStop plus `KillMode=mixed`, after a few small adjustments. Mixed alone is not enough. This fits inside the authorized trial as long as it's disclosed. The real proof is still the one GPU stop retest.

**Is ExecStop + mixed necessary and sufficient?**
- Mixed alone isn't enough. systemd would SIGTERM only the launcher, and the launcher's path is terminate the manager, wait 20s, then SIGKILL the manager. If the manager is SIGKILLed or exits before the container stops, systemd's final SIGKILL hits the rest of the cgroup, including conmon. That is the same conmon loss as before. ExecStop is the part that actually stops the container in order. Mixed is the supporting part.
- ExecStop + mixed is necessary but not proven sufficient, for two reasons:
  - **The GPF may not be explained by the race.** `podman stop` still sends SIGTERM to llama-server. A libc GPF while handling SIGTERM could come from llama-server's own teardown under load, not only from the concurrent signals and conmon loss. Earlier clean `podman stop` and router-unload exits make the race hypothesis plausible, not proven. The CPU sleep-container test only checks the systemd/conmon mechanics. It can't test the GPF.
  - **Fans are still at risk.** With mixed, once the launcher exits, anything left in the cgroup (including the fan wrapper) gets SIGKILL. If the launcher's shutdown doesn't gracefully stop the fan wrapper before exiting, `pwm_enable` can be left manual again. Add `ExecStopPost=-<fanwrapper> --restore`, but only if `--restore` is idempotent and safe when nothing is running. Then fan restore doesn't depend on shutdown ordering.

**Adjustments to the drop-in:**
- Write it as `ExecStop=-/usr/bin/podman stop --time 20 <name>`. The leading `-` means a missing container (exit 125) or another error won't mark the unit failed. That covers the Qwen-active case, and later name drift.
- If the base unit or an earlier drop-in already has an ExecStop, this one appends to it. Put a bare `ExecStop=` line first if you mean to replace it. Afterwards, confirm the effective values with `systemctl --user show -p ExecStop,ExecStopPost,KillMode,TimeoutStopSec`. Also check that no later-sorting drop-in overrides them.
- The timeout budget is tight: up to 20s for `podman stop` plus 20s launcher wait plus margin. `TimeoutStopSec=60` probably works, but 90 is safer.
- Make sure the manager doesn't treat the backend exit during ExecStop as a crash and restart or reload it. If you have a minute, grep for restart-on-exit logic in the launcher or manager.

**Rollback flaws:**
- Don't rely on the new drop-in to stop the service during rollback, since that stop path is what's under test. Run an explicit `podman stop --time 20 <new container>` first, confirm the GPU resources are released, then `systemctl --user stop`.
- After moving the drop-in out and running `daemon-reload`, check with `systemctl show` that ExecStop and KillMode are back to their original values before starting the launcher. Add the same check to `--check`.
- The old production config may have the same concurrent-SIGTERM race. Its stop path was never shown clean. Record this as a possible pre-existing issue, not something the candidate introduced.

**Scope:**
- This is within the authorized deployment-with-rollback: it lives in a trial-specific drop-in, the rollback removes it, and no shared code changes. But it changes stop behavior for every backend the service runs, including Qwen 27B. State that plainly, and record the Qwen stop path as not validated. No new decision is needed unless the drop-in is meant to outlive the trial.
